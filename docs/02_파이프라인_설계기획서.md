## 0. 요약

### 핵심 설계 네 가지

1. **말 끝 판단에 시간을 쓰고, 그 시간에 답을 미리 만든다.**
   고객이 잠깐 쉴 때마다 그때까지의 받아쓰기로 LLM 답을 미리 만들어 둔다(이하 "추측 실행"). 말이 끝났다고 확정하는 순간(이하 "커밋")에는 준비된 결과를 바로 쓴다. 1.5초 예산을 LLM 대기가 아니라 "정말 끝났는가"를 확인하는 데 쓴다.
2. **소리와 함수 호출은 커밋 뒤에만 나가고, 추측 결과는 검증한 뒤에만 쓴다.**
   커밋 전에 고객이 다시 말하면 조용히 버린다. 커밋할 때는 추측에 쓴 받아쓰기가 확정 받아쓰기와 같은지 확인한다. 끼어들기와 잘못된 함수 호출을 구조적으로 막는다.
3. **자주 쓰는 말은 미리 합성해 둔다.**
   TTS가 가장 느리고 한도도 불확실하다. 안내 문구, 정보 요청 질문, 대표 답변을 미리 합성해 지연과 요청 수를 함께 줄인다.
4. **정책은 측정으로 정한다.**
   연습 문항의 음성과 말 끝 시각으로 종료 정책을 재생 실험하고, 응대 프롬프트는 채점기 점수로 고친다. 이 실험 기록이 그대로 발표의 근거가 된다.

### 목표 수치 (연습 문항 기준, 목표값이며 예측이 아님)

| 지표 | 목표 |
|---|---|
| 끼어들기(말 도중 발화) | 0건 |
| 첫 소리 | 중앙값 1.0초 이하, 90% 지점 1.5초 이하 (95% 지점도 함께 보고) |
| 함수 결과 뒤 답 첫 소리 | 중앙값 2.0초 이하 |
| 응대 점수 | 0.85 이상 |
| 함수 정확도 | 0.90 이상 |
| 중립 첫마디("네, 고객님.") 사용 비율 | Plan A 20% 이하. Plan B·C는 답 음성 대기 한도로 조절 (7.4절) |
| 동시 4건 처리 | 오류 0, 지연 열화 10% 이내 |

## 1. 점수 구조에서 나온 전략

### 1.1 문항 하나의 손익

시스템 점수는 문항마다 `0.5×응대 + 0.2×함수 + 0.3×속도`다.

| 사건 | 문항 점수 손실 |
|---|---|
| 첫 소리가 0.5초 늦어짐 (1.5초 초과 구간) | 속도 10점 × 0.3 = 3점 |
| 말 도중에 소리를 냄 | 속도 0점으로 30점 손실. 말을 다 못 들었으므로 응대와 함수도 틀릴 가능성이 높아 최대 100점 손실 |
| 응대가 틀림 | 50점 |
| 불필요한 함수 호출 또는 잘못된 인자 | 20점 |

결론

- 0.5초를 더 기다려 끼어들기 확률을 3%포인트 넘게 줄일 수 있으면 기다리는 쪽이 이득이다. 종료 판단은 보수적으로 한다.
- 추측 결과가 틀렸을 때 다시 실행하는 비용(지연 수 점)은 틀린 답을 내보내는 비용(50점)보다 훨씬 작다. 검증에서 조금이라도 다르면 다시 실행한다.
- 응대 정확도가 비중 50%로 가장 크다. 속도 최적화보다 프롬프트 반복 개선에 사람을 더 배치한다.

### 1.2 사람이 평가하는 80점

| 항목 | 배점 | 우리가 준비할 것 |
|---|---|---|
| 사용자 경험 | 50 | 여러 턴이 이어지는 실제 통화 시연, 끼어들기 대응, 짧고 또렷한 답 |
| 발표·질의응답 | 20 | 개선 전후 수치, 검토한 대안과 버린 이유 |
| 기획서 | 10 | 템플릿 항목 전부, 측정 결과 별첨 |

- 전체 100점 중 속도가 직접 차지하는 몫은 6점(20점의 30%)이다. 다만 사용자 경험 기준에 "응답 속도가 자연스러운가"가 있고 발표 6번 슬라이드가 속도 전용이라, 속도 작업은 세 항목에 걸쳐 쓰인다.
- 측정기는 한 턴짜리 문항만 보내지만 사용자 경험 평가는 "말하는 도중 개입"과 "돌발 상황 대응"을 본다. 같은 서버에 여러 턴 통화와 끼어들기를 지원하는 시연 모드를 둔다.
- 시연 모드는 50점짜리 항목의 재료다. 행사 전에 뼈대를 만들고, 15:00 Mid Review에서 실제로 보여 준다.

### 1.3 측정 시각을 모른다는 점

시스템 측정은 "오후"라고만 되어 있고, 측정 중에는 서버를 고칠 수 없다. 점심 이후로는 항상 측정 가능한 안정 버전을 켜 두고, 개발은 다른 포트에서 한다.

## 2. 설계 원칙

| 원칙 | 내용 |
|---|---|
| 커밋 게이트 | 커밋 전에는 음성도 함수 호출도 내보내지 않는다 |
| 검증 뒤 채택 | 추측 결과는 확정 받아쓰기와 일치할 때만 쓴다 |
| 준비는 미리, 실행은 확정 뒤 | LLM 판단은 앞당기고, 되돌릴 수 없는 일은 커밋 뒤에 한다 |
| 지정 모델만 사용 | STT, TTS, LLM 외의 AI 모델을 넣지 않는다. 종료 판단은 Soniox의 종료 감지와 GPT-5.4 mini, 규칙으로 한다 |
| 침묵으로 끝나지 않는다 | 어떤 오류에도 대체 음성과 `turn.end`를 보낸다 |
| 모든 단계에 시각을 남긴다 | 단계별 타임스탬프를 세션마다 기록해 병목과 개선 폭을 숫자로 말한다 |
| 채움말이 아니라 안내 | 첫마디는 사람 상담원이 실제로 하는 말만 쓴다. 직접 답할 수 있으면 첫마디 없이 답부터 말한다 |
| 측정을 왜곡하지 않는다 | 전송 순서와 속도를 점수에 유리하게 꾸미지 않는다 |


- 상담원 서버와 모의 함수 서버는 별도 프로세스다. 상담원 서버는 모의 함수 서버 주소를 모른다. 항상 `session.start`의 `tools_url`만 쓴다.
- 서버 시작 시 한 번 하는 일: OpenAI·Gemini 연결 예열, 프롬프트 캐시 예열, 첫마디와 정형 문장 음성 합성(디스크에 저장해 재시작 때 재사용).
- 서버가 떠 있는 동안 계속 하는 일: 4분마다 최소 출력의 요청을 보내 프롬프트 캐시와 연결을 살려 둔다. 측정이 시작되는 첫 4문항이 캐시 없이 나가지 않게 한다.

## 4. 한 턴의 흐름

용어

| 용어 | 뜻 |
|---|---|
| 쉼 | 말소리 뒤에 무음이 350ms(초기값) 이어진 상태. 끝일 수도, 중간 쉼일 수도 있다 |
| 추측 실행 | 쉼이 생겼을 때 그때까지의 받아쓰기로 LLM 답을 미리 만드는 것. 기본은 LLM까지만 한다 |
| 추측 합성 | 추측 실행의 답을 커밋 전에 TTS까지 해 두는 것. 기본은 끈다 (5.6절) |
| 커밋 | 말이 끝났다고 확정하는 시점. 이후에는 되돌리지 않는다 |
| 첫마디 | 미리 합성해 둔 짧은 안내 음성. 예: "네, 주문 내역 확인해 드리겠습니다." |
| 정형 문장 | 미리 합성해 둔 질문·안내·대표 답변. LLM이 같은 문구를 내면 합성 없이 재생한다 |

### 4.1 직접 답하는 문항 (함수 없음)

```
고객 말 ──────────────┤말 끝
무음                   ├─350ms─┤쉼 감지
추측 실행                       ├─ LLM 답 생성 ─┤             (커밋 전이므로 아무것도 내보내지 않음)
종료 판단                       ├── <end> 대기, 완결성 확인 ──┤커밋
커밋 처리                                                      ├ 받아쓰기 일치 검증 ┤
음성 출력                                                                          ├▶ 답 음성 ─▶ turn.end
```

커밋 뒤 답 음성이 나가는 세 가지 경우

| 경우 | 첫 소리 |
|---|---|
| 답이 정형 문장과 일치 | 캐시 음성을 즉시 보낸다 |
| 자유 생성 답, 추측 합성이 켜져 있고 준비됨 | 준비된 음성을 즉시 보낸다 |
| 자유 생성 답, 합성이 아직 안 됨 | 합성을 시작하고, 답 음성 대기 한도(측정 1.35초, 시연 1.8초)를 넘기면 중립 첫마디를 먼저 보낸다 |

### 4.2 함수를 호출하는 문항

```
고객 말 ──────────────┤말 끝
추측 실행                       ├─ LLM이 "함수 X를 인자 Y로" 결정 ─┤   (호출은 보류)
종료 판단                                                           ┤커밋, 검증
음성 출력                                                           ├▶ ① 첫마디 전송 완료
함수 호출                                                              ├─ ② POST tools_url ─┤결과
두뇌 2차                                                                                    ├─ 결과로 답 생성 ─┤
TTS                                                                                                            ├─ 합성 ─┤▶ 답 음성 ─▶ turn.end
```

- 순서를 고정한다. 첫마디 음성을 웹소켓으로 다 보내고 150ms 뒤에 함수를 호출한다(측정 모드). 첫 소리에는 영향이 없고, 조회 뒤 답 시간은 함수 응답부터 재므로 그대로다. 보낸 직후 바로 부르면 측정기가 프레임을 다 처리하기 전에 함수 응답이 찍혀 첫마디 꼬리가 답으로 잡혔다.
- 중립 첫마디를 이미 냈으면(4.4절 5단계) 측정 모드에서는 함수 안내 첫마디를 생략하고, 시연 모드에서는 "네,"를 뺀 이어 말하기 문구("주문 내역 확인해 드리겠습니다.")를 쓴다.
- 시연 모드에서는 첫마디 재생과 함수 호출을 동시에 진행한다.
- 이유: 측정기는 "마지막 함수 응답 뒤에 도착한 첫 유성 프레임"으로 조회 뒤 답 시간을 잰다. 첫마디의 뒷부분이 함수 응답보다 늦게 도착하면 첫마디가 답으로 잡혀 측정이 왜곡된다.
- 속도 점수는 첫 소리와 조회 뒤 답의 평균이므로 2차 답의 지연도 줄인다(5.4절, 5.6절).

### 4.3 고객이 다시 말하는 경우

커밋 전에 말소리가 다시 들리면 진행 중인 추측 실행을 취소하고 계속 듣는다. 아무것도 내보내지 않았으므로 벌점이 없다.

### 4.4 커밋할 때의 처리 순서

1. **확정 받아쓰기를 얻는다.** `<end>`를 받았으면 이미 확정된 토큰을 쓴다. 받지 못했으면 `finalize`를 한 번 보내고 `<fin>`을 최대 300ms 기다린다.
2. **받아쓰기가 끝까지 왔는지 확인한다.** Soniox가 알려 주는 처리 진행값(`final_audio_proc_ms`)이 마지막 말소리 위치를 넘었는지 본다. 둘 다 음성 스트림 기준 ms다(보낸 PCM 바이트 ÷ 32). 못 넘었으면 20ms 간격으로 다시 보되, 1~2단계 합계 300ms를 넘기지 않는다. 어미가 작게 끝나는 발화에서 마지막 토큰을 놓치지 않기 위해서다.
3. **추측에 쓴 받아쓰기와 비교한다.** 공백과 문장부호를 뺀 뒤 글자가 같으면 추측 결과를 채택한다. 조금이라도 다르면 버리고 확정 받아쓰기로 다시 실행한다. 번호의 마지막 자리가 확정 단계에서 바뀌는 경우를 막는다.
4. **Soniox 스트림을 닫는다.** 측정 모드에서는 한 턴뿐이므로 빈 텍스트 프레임을 보내고 연결을 닫는다. 예외가 나도 닫히도록 정리 구문에 넣는다. 동시 스트림 한도가 10개라 새면 반복 측정 중에 막힌다.
5. **LLM 결정을 기다린다.** 결정이 아직이면 말 끝 추정 시각에서 1.2초까지 기다린다. 그 안에 결정이 나오면 그에 맞는 첫마디나 답을 낸다. 넘으면 중립 첫마디를 내고 그 사실을 기록한다(이후 첫마디 중복 방지). 함수 호출 여부를 모르는 채로 "확인해 드리겠습니다"를 먼저 말하지 않는다. 이 한도는 답 음성 대기 한도(4.1절)와 별개다.
6. **갈라진다.** 함수 호출이면 4.2절, 직접 답이면 4.1절.

추측 적중률(검증을 통과한 비율)과 중립 첫마디 사용 비율을 세션마다 기록한다.

## 5. 모듈 설계

### 5.1 세션과 프로토콜

- 연결 직후 `session.start`를 받는 즉시 Soniox 연결을 별도 태스크로 연다. 고객 음성 수신을 막지 않는다. 연결되는 동안 들어온 음성은 모아 두었다가 설정 메시지 뒤에 한꺼번에 보낸다(Soniox 권장 방식).
- 고객 음성은 Soniox와 무음 측정기에 동시에 넣는다.
- 커밋 뒤에도 측정기가 보내는 무음은 계속 읽어서 버린다. 읽지 않으면 연결이 밀린다.
- 우리가 한 말은 `agent.transcript` 텍스트로도 보낸다.
- `history` 형식은 09:00에 확인해 변환 함수 하나에서만 처리한다.

감시 타이머 (어떤 경우에도 25초 제한 전에 `turn.end`를 보낸다)

| 상황 | 조건 | 동작 |
|---|---|---|
| 말이 전혀 감지되지 않음 | `session.start` 뒤 10초 동안 말소리도 Soniox 토큰도 없음 | "말씀이 잘 들리지 않습니다" 대체 음성과 `turn.end` |
| 응답이 늦어짐 | 마지막 말소리 또는 마지막 새 토큰 중 늦은 시각에서 20초 경과 | 진행 상태와 무관하게 대체 음성과 `turn.end` |
| 소음으로 무음이 잡히지 않음 | 5.3절의 소음 경로 | 토큰 기준으로 커밋 |

"시작 뒤 40초" 같은 절대 시간 하나만 두는 방식은 쓰지 않는다. 발화가 12초면 25초 제한이 37초에 걸려 이미 늦다.

### 5.2 STT (Soniox `stt-rt-v6`)

초기 설정

```json
{
  "model": "stt-rt-v6",
  "audio_format": "pcm_s16le", "sample_rate": 16000, "num_channels": 1,
  "language_hints": ["ko"],
  "enable_endpoint_detection": true,
  "endpoint_latency_adjustment_level": 1,
  "endpoint_sensitivity": 0.0,
  "max_endpoint_delay_ms": 3000,
  "context": {
    "general": [
      {"key": "domain", "value": "건강기능식품 쇼핑몰 고객센터 전화 상담"},
      {"key": "business name", "value": "(브랜드명)"},
      {"key": "caller", "value": "(session.start의 발신자 이름)"}
    ],
    "terms": ["(상품명, 성분명, 브랜드 고유 용어)"],
    "text": "(상담 유형과 자주 나오는 표현 요약)"
  }
}
```

| 설정 | 선택 | 이유 |
|---|---|---|
| `max_endpoint_delay_ms` | 3000 (최대) | 값이 작으면 문장 중간의 긴 쉼에서도 강제로 종료 신호가 난다. 상한을 넓혀 의미 판단에 맡긴다 |
| `endpoint_latency_adjustment_level` | 1에서 시작 | 0, 1, 2를 연습 문항으로 비교해 정한다 |
| `terms` | 상품명·성분명만 | 문서가 숫자, 코드, 전화번호는 넣지 말라고 한다 |
| 발신자 정보 | 통화마다 추가 | 문서 권장. 이름 인식에 도움 |
| 접속 주소 | 키의 리전에 맞춤 | 키가 일본 리전이면 `stt-rt.jp.soniox.com`을 써야 한다. 리전은 우리가 고르는 것이 아니라 받은 키로 정해진다. 09:00에 확인 |

받아쓰기를 다루는 원칙

- **STT 원문은 고치지 않고 LLM에 그대로 넘긴다.** "공일공 일이삼사"를 숫자로, "데모"를 `DEMO`로 바꾸는 일은 문맥을 아는 LLM이 한다. 코드로 원문을 미리 고치면 "이 상품", "하나만 취소" 같은 일반 표현이 망가질 수 있다.
- 숫자 읽기 파서는 만들되 종료 판단의 자릿수 세기에만 쓴다(5.3절). 파서가 틀려도 대기 시간이 달라질 뿐 답이 틀리지는 않는다.
- 추측 실행은 비최종 토큰을 포함한 받아쓰기로 한다. 커밋할 때 확정 받아쓰기와 비교한다(4.4절).
- `finalize`는 커밋할 때 `<end>`가 없는 경우에만 한 번 보낸다. 문서가 자주 보내지 말라고 한다.

실험할 것 (여유가 있을 때)

- 상담원 텍스트 입력: `history`의 마지막 상담원 발화를 고객 음성 앞에 `agent_text`로 보낸다. 짧은 답("네", 숫자만 말하는 답)의 인식이 좋아지는지 본다.

### 5.3 종료 판단

신호 세 가지

| 신호 | 얻는 방법 | 성격 |
|---|---|---|
| 무음 길이 | 20ms 프레임의 RMS가 임계값 미만으로 이어진 시간 | 즉시, 확실. 측정기와 같은 기준이라 말 끝 시각도 추정 가능 |
| Soniox `<end>` | 종료 감지 토큰 | 억양과 문맥을 본 의미 판단 |
| 완결성 | 규칙으로 먼저 판정하고, 애매하면 GPT-5.4 mini에 한 토큰짜리 판정 요청 | 독립적인 두 번째 의견 |

무음 임계값

- 기본은 300이다. 측정기가 말 끝을 정하는 기준과 같다.
- 09:00에 연습 음성의 소음 바닥을 잰다. 바닥이 높으면 `max(300, 소음 바닥 × 2.5)`로 올린다.
- 데모 음성은 무음 구간이 완전한 0이라 300으로 충분했다.

완결성의 기준: 문장이 문법적으로 끝났는지가 아니라 **지금 답할 내용이 있는지**를 본다.

| 판정 | 받아쓰기의 모습 | 예 |
|---|---|---|
| 완결 | 물음이나 요청이 종결 어미와 문장부호로 끝남 | "택배가 어디쯤 왔는지 알 수 있을까요?" |
| 완결 | 직전 상담원 발화가 예·아니오 질문이고 답이 단답 | "네", "아니요", "네 부탁드려요" |
| 완결 | 직전 상담원 발화가 번호 요청이고, 말한 숫자의 자릿수가 다 참 | 전화번호 11자리. 주문번호 자릿수는 09:00 규격으로 확정 |
| 서두 | 인사, 부르는 말, 용건 예고뿐 | "안녕하세요.", "여보세요?", "문의 좀 드리려고요." |
| 미완결 | 쉼표나 연결 어미로 끝남, 번호의 자릿수가 모자람, 머뭇거리는 말 | "주문번호가 1234인데,", "공일공 일이삼", "어…" |
| 미정 | 양쪽 다 가능한 형태. LLM 판정을 요청 | "~는데요", "~인데요" |

- "서두"를 따로 두는 이유: 인사는 문법적으로 완결된 문장이라 Soniox도 종료 신호를 낼 수 있다. 데모 문항 DEMO1이 "안녕하세요," 뒤에 620ms를 쉬고 본론을 말한다. 1초 넘게 쉬는 고객이면 인사 직후에 끼어들게 된다.
- LLM 판정은 추측 실행과 동시에 따로 보낸다. 입력은 직전 상담원 발화와 고객 발화뿐이라 짧고 빠르다.

커밋 규칙 (초기값, 연습 문항으로 조정)

| 순서 | 조건 | 동작 |
|---|---|---|
| 1 | `<end>` 수신, 무음 300ms 이상, 완결 | 커밋 |
| 2 | `<end>` 없음, 완결, 무음 900ms 이상 | 커밋 |
| 3 | `<end>` 수신, 미완결 | 무음 1,600ms에 커밋 |
| 4 | 서두 | 무음 2,400ms에 커밋 (`<end>` 수신 여부와 무관) |
| 5 | 무음 2,400ms 이상 | 무조건 커밋 (끝없이 기다리지 않는다) |
| 미정 | LLM 판정이 아직 오지 않음 | 판정을 기다린다. 무음 1,200ms를 넘으면 미완결로 간주하고 규칙 3, 5를 따른다 |
| 소음 경로 | RMS가 임계값 아래로 내려가지 않는데 `<end>`를 받았고 새 토큰이 800ms 동안 없음 | 커밋 |
| 취소 | 커밋 전에 말소리 재개 | 추측 결과를 버리고 계속 듣는다 |

- 규칙 4, 5로 커밋되면 답은 대개 인사 응대나 되묻는 질문이 된다. 첫 소리 2.4초면 속도 80점이다. 인사만 하고 끝나는 문항에서 20점(문항 점수로 6점)을 내주고, 인사 뒤에 끼어드는 사고를 막는다.
- 임계값은 8.3절의 재생 실험으로 정한다. 연습 문항과 시험 문항은 같은 상담 기록에서 뽑으므로 연습 문항으로 맞춘 값이 유효하다.

추측 실행을 시작하는 시점

| 규칙 판정 | 시작 시점 |
|---|---|
| 완결, 미정 | 쉼을 감지한 즉시 (무음 350ms) |
| 미완결, 서두 | 무음 800ms |

- 미완결로 보일 때 아예 시작하지 않으면, 실제로는 말이 끝난 경우 2.4초에 커밋하고도 답이 준비되어 있지 않다. 그래서 늦춰서 시작한다.
- 쉼 임계값 350ms와 800ms는 재생 실험에서 "문항당 헛된 추측 횟수"와 "커밋 시 준비 비율"을 보고 정한다.

### 5.4 두뇌 (GPT-5.4 mini)

호출 형태

- 스트리밍. 함수 정의는 `GET {tools_url}/tools`에서 받는다. 골격 서버가 이미 OpenAI 형식으로 돌려준다. 주소별로 한 번만 받아 둔다.
- 함수 정의는 이름순으로 정렬하고 항상 같은 방식으로 직렬화한다. 순서가 바뀌면 캐시가 깨진다.
- 답의 길이는 프롬프트("한두 문장")로 제어한다. 출력 상한은 추론 토큰까지 포함하므로 안전 상한만 둔다: 추론 강도 none일 때 400, low 이상일 때 1024. 잘리면(`finish_reason: length`) 상한을 두 배로 한 번 다시 부른다. `prompt_cache_key`를 고정한다.
- 추론 강도는 세 구성을 비교해 정한다: 전부 `none`, 전부 `low`, 1차 판단은 `low`에 2차 요약은 `none`. 추론 강도가 다르면 캐시가 따로 잡힐 수 있으므로 쓰는 구성마다 예열한다.

메시지 구성 (앞부분이 모든 요청에서 같아야 캐시가 적중한다)

| 순서 | 내용 | 변하는가 |
|---|---|---|
| 1 | 역할, 말투 규칙, 출력 규칙, 판단 절차 | 고정 |
| 2 | 응대 매뉴얼 전문, 브랜드·상품 정보 | 고정 |
| 3 | 업무별 정책 표 (아래) | 고정 |
| 4 | 정형 문장 목록, 예시 문항에서 고른 모범 응대 | 고정 |
| 5 | 현재 시각과 날짜 표, 발신자 정보, 대화 이력 | 세션마다 |
| 6 | 이번 고객 발화 (STT 원문 그대로) | 턴마다 |

업무별 정책 표 (매뉴얼을 읽고 09:30~10:30에 만든다)

| 업무 | 필수 확인 정보 | 호출하는 조건 | 호출하면 안 되는 조건 | 인계 조건 |
|---|---|---|---|---|
| (배송 조회 등 업무마다 한 줄) | | | | |

매뉴얼 원문만 주는 것보다, 함수 채점 기준("맞는 때에", "호출하면 안 될 때")에 맞춘 표를 함께 주는 쪽이 판단이 안정적이다.

날짜 표 (코드로 계산해 5번 자리에 넣는다)

```
현재: 2026-11-21 (토) 11:00 | 어제: 11-20 (금) | 내일: 11-22 (일) | 7일 전: 11-14 (토)
```

반품 기한, 주말과 영업일, 출고 마감 같은 날짜 계산을 LLM의 암산에 맡기지 않는다. 필요한 기준일은 매뉴얼의 정책을 보고 추가한다.

출력 규칙 (프롬프트에 명시)

- 전화 말투의 한국어. 한두 문장. 핵심부터.
- 답을 "네, 고객님"이나 "안녕하세요" 같은 상투적인 서두로 시작하지 않는다. 고객이 인사만 한 경우는 예외다.
- 목록, 기호, 괄호, URL, 이모지를 쓰지 않는다. 음성으로 읽히는 글만 쓴다.
- 매뉴얼과 함수 결과에 없는 사실은 말하지 않는다. 모르면 확인이 어렵다고 말하고 인계 기준을 따른다.
- 이미 받은 정보를 다시 묻지 않는다. 대화 이력과 발신자 정보를 먼저 본다.
- 함수를 호출할 때는 글을 함께 쓰지 않는다. 안내 문구는 시스템이 이미 말했다. 결과 답에서는 그 안내를 반복하지 말고 결과부터 말한다.
- 자주 쓰는 문장은 정형 문장 목록의 문구 그대로 쓴다(5.7절).

번호를 다루는 규칙 (프롬프트의 예시로 보여 준다)

- 숫자 읽기("공일공", "일 공 공 일", "천이백삼십사")를 숫자로 바꾼다. 영문 접두어의 한글 발음("데모")은 원래 표기로 바꾼다.
- 고객이 스스로 고친 경우("1001, 아 아니 1002번이요") 마지막에 말한 값을 쓴다.
- 인자의 형식(하이픈, 대소문자, 자릿수)은 함수 설명과 예시를 따른다. 하이픈을 일괄로 빼지 않는다.

판단 절차 (프롬프트에 명시)

1. 문의 유형을 정한다.
2. 그 유형에 필요한 정보가 대화 이력, 발신자 정보, 이번 발화에 있는지 본다.
3. 인계 조건에 해당하면 인계한다.
4. 정보가 부족하면 함수를 부르지 않고 필요한 것 하나만 묻는다.
5. 정보가 충분하면 함수를 부른다. 조회·변경이 필요 없는 안내는 바로 답한다.

함수 호출 규율 (코드에서 강제)

| 규칙 | 이유 |
|---|---|
| 커밋과 검증 뒤에만 실행 | 덜 들은 번호로 호출하면 "잘못된 호출"로 채점된다 |
| 응답에 함수 호출이 있으면 함께 온 글은 버린다 | 캐시 첫마디와 겹쳐 같은 말을 두 번 하게 된다 |
| 한 응답에 함수 호출이 여러 개면 동시에 실행한다 | 지연 단축 |
| 연쇄 호출은 한 턴에 최대 2회전. 두 번째 회전에서는 첫마디를 다시 내지 않는다 | 25초 제한 보호, 중복 안내 방지 |
| 호출 직전의 정규화는 앞뒤 공백 제거만 기본. 하이픈 제거·대문자화는 연습 데이터의 인자 형식을 보고 설정으로 켠다 | 실제 데이터가 하이픈을 포함할 수 있다 |
| 검증은 최소한으로: 빈 값, "unknown" 같은 자리 채움 값, 명백한 자릿수 미달만 막는다 | 엄격한 패턴 검사는 정상 번호를 막을 수 있다 |
| "혹시 몰라서" 호출 금지 | 호출하면 안 될 때의 호출도 틀린 것으로 채점된다 |
| 실패·시간 초과 시 한 번 재시도, 그래도 실패면 사과와 인계 | 침묵 방지 |
| 중립 첫마디를 냈으면 답의 앞에서 같은 서두를 지운다 | "네, 고객님. 네, 고객님" 방지 |

조회 뒤 답을 빠르게 하는 방법

- 2차 호출은 1차와 같은 앞부분에 함수 결과만 덧붙인다.
- 결과가 정해진 접수형 함수(예: 콜백 접수 성공)는 정형 문장 음성으로 바로 답한다.
- 첫 문장을 먼저 합성할지는 5.6절의 실측으로 정한다.

### 5.5 함수 호출 클라이언트

- `POST {tools_url.rstrip("/")}/tools/{name}`, 헤더 `X-Session-Id: {session_id}`, JSON 본문.
- 연결을 재사용하는 비동기 클라이언트 하나를 모든 세션이 공유한다.
- 첫마디 음성 전송이 끝난 뒤에 호출한다(4.2절).
- 시간 제한 5초. 호출 시각과 응답 시각을 기록한다.

### 5.6 TTS (Gemini 2.5 Flash TTS)

| 항목 | 설계 |
|---|---|
| 호출 | 비동기 클라이언트의 `client.aio.models.generate_content_stream`. 동기 클라이언트는 이벤트 루프를 막아 동시 세션 전체가 멈춘다 |
| 모델과 요청 | `gemini-2.5-flash-preview-tts`, `response_modalities: ["AUDIO"]`, prebuilt voice |
| 말투 지시 | 짧은 고정 문구를 본문 앞에 붙인다. 지시문을 소리 내어 읽는지 반드시 확인한다 |
| 음성 선택 | 후보 몇 개를 같은 문장으로 합성해 또렷함과 브랜드 말투 규칙으로 고른다 |
| 요청 횟수 | 기본은 응답당 1회. 호출마다 억양과 속도가 조금씩 달라서, 짧은 답을 나누면 문장 사이에 목소리가 튄다 |
| 2분할 조건 | 실측에서 글이 길수록 첫 음성이 뚜렷이 늦어지고 한도가 넉넉할 때만 쓴다 |
| 앞 무음 정리 | 임계값에 도달한 지점의 20~30ms 앞부터 살리고 5ms 페이드인을 건다. 칼같이 자르면 ㅅ, ㅎ, ㄱ 같은 약한 초성이 잘린다 |
| 변환 | 24kHz에서 16kHz로. 조각 하나의 변환은 1ms 미만이라 이벤트 루프에서 바로 한다 |
| 음량 | 캐시 음성과 실시간 음성의 평균 음량을 비교해, 차이가 귀에 들리면 고정 이득으로 맞춘다 |
| 동시성 | 세마포어로 동시 요청 수를 제한한다. 값은 실측한 한도에 맞춘다 |
| 실패 처리 | 4초 안에 음성이 없으면 한 번 재시도, 그래도 없으면 대체 음성 |
| 결과 캐시 | 문장 텍스트의 해시로 합성 결과를 저장한다. 같은 문장은 다시 합성하지 않는다 |

추측 합성 (기본은 끔)

- 켜는 조건: 한도에 여유가 있다고 실측된 경우(7.4절의 Plan A).
- 켜더라도 쉼마다 합성하지 않는다. `<end>`를 받았거나, 완결 판정 뒤 무음이 500ms 이어졌을 때만 합성한다.
- 정형 문장과 일치하는 답은 합성할 필요가 없다.

TTS 입력 변환 (`textnorm.py`의 중심)

LLM이 쓴 글을 TTS가 틀리게 읽으면 채점기의 받아쓰기에서 사실이 틀린 답이 된다. 09:00 실측 스크립트가 10개 표기를 합성해 Soniox로 되받아쓰고, 실제로 틀리는 표기만 변환을 켠다.

| 대상 | 예 | 바꿀 형태 | 기본 |
|---|---|---|---|
| 전화번호 | 010-1234-5678 | 자릿수 읽기 (공일공 일이삼사 오육칠팔) | 켬 |
| 주문번호 | DEMO1001 | 접두어와 자릿수 읽기. 규격에 맞춰 확정 | 켬 |
| ISO 날짜 | 2026-11-21 | 11월 21일. 연도가 현재와 다르면 2025년 6월 10일처럼 연도를 남긴다 | 켬 |
| 물결·퍼센트 | 3~5일, 10% | 3에서 5일, 10 퍼센트 | 켬 |
| 금액 | 39,800원 | 삼만 구천팔백 원 | 끔 |
| 한글 월일 | 6월 10일 | 유월 십일 (6월은 유월, 10월은 시월) | 끔 |

- 변환한 문장을 합성한 뒤 Soniox로 다시 받아써서 원문과 같은지 확인한다. 어긋나는 표기는 규칙에 추가한다. 지정 모델만으로 하는 자체 검증이다.
- 채점 대상이 음성 받아쓰기가 아니라 `agent.transcript` 텍스트로 확인되면 이 작업의 우선순위를 낮춘다(7.4절).

Cloud Text-to-Speech 경로(`gemini-2.5-flash-tts`, 스트리밍 합성 API)의 키를 받게 되면 벤치마크한 뒤 빠른 쪽 하나만 남긴다.

### 5.7 첫마디와 정형 문장 캐시

서버 시작 시 지정 TTS로 합성해 16kHz PCM으로 저장한다. 같은 음성, 같은 말투다.

| 종류 | 예시 | 쓰는 때 |
|---|---|---|
| 조회 안내 | "네, 주문 내역 확인해 드리겠습니다." "네, 바로 조회해 드릴게요." | 조회형 함수 호출 직전 |
| 접수 안내 | "네, 접수 도와드리겠습니다." | 접수형 함수 호출 직전 |
| 중립 | "네." "네, 고객님." "네, 말씀 잘 들었습니다." "네, 알겠습니다." | 결정 대기 1.2초를 넘겼을 때. 내용과 무관한 문구만 쓴다 |
| 중립(안내) | "네, 안내해 드리겠습니다." "네, 말씀드리겠습니다." | 답이 정해졌는데 음성이 늦을 때, 답이 질문이 아닌 경우 |
| 이어 말하기 | "주문 내역 확인해 드리겠습니다." | 시연 모드에서 중립 첫마디 뒤에 함수를 부를 때 |
| 정형 질문 | "주문번호를 말씀해 주시겠어요?" "주문하신 분 성함과 연락처를 말씀해 주시겠어요?" | LLM이 같은 문구를 출력하면 합성 없이 즉시 재생 |
| 정형 안내 | 인계 안내, 접수 완료 안내 | 위와 같음 |
| 대표 답변 | 상담 시간, 배송비, 반품 기한처럼 매뉴얼에 답이 고정된 문의의 답 | 위와 같음. 아래 조건을 통과한 것만 |
| 대체 음성 | "죄송합니다, 다시 한 번 말씀해 주시겠어요?" | 오류, 시간 초과 |

- 함수별 안내 문구 대응표는 09:00에 함수 정의를 보고 채운다. 문구는 매뉴얼의 말투 규칙에 맞춘다.
- 같은 종류에 문구를 2~3개 두고 돌려 쓴다. "같은 채움말 반복" 감점을 피한다.
- 정형 문장은 프롬프트에 목록으로 넣어 LLM이 글자 그대로 쓰게 한다.
- 대표 답변 캐시의 조건: 텍스트 전용 평가에서 자유 생성 답보다 응대 점수가 낮지 않을 때만 쓴다. 고정된 답은 고객이 실제로 물은 것과 조금 어긋날 수 있다. 규모는 TTS 한도에 따라 정한다(7.4절).
- 측정 모드에서는 첫마디 음성 끝에 무음 200ms(초기값, 들어 보고 조정)를 붙인다. 측정기의 녹음은 받은 프레임을 그대로 이어 붙이므로, 무음이 없으면 첫마디와 답이 숨 쉴 틈 없이 붙는다. 무음 프레임은 시간 측정에 영향이 없다.

### 5.8 음성 출력

- 측정 모드: 합성되는 대로 바로 보낸다. 측정기는 도착 시각을 재므로 재생 속도에 맞추지 않는다.
- 측정기는 RMS 300 이상인 첫 프레임을 첫 소리로 본다. 앞 무음을 정리해 첫 조각에 말소리가 들어가게 한다.
- 모든 음성을 보낸 뒤에 `turn.end`를 보낸다.
- 측정 수치를 좋게 보이려고 전송 순서나 속도를 꾸미지 않는다.

### 5.9 모의 함수 서버

- 스타터킷 골격을 유지한다. 측정기가 쓰는 `/tools`, `/tools/{name}`, `/calls`가 이미 맞춰져 있다.
- 고칠 것: `0.0.0.0` 바인딩, 데이터·함수 정의 파일을 실행 인자로 받기, `lookup()` 구현, `protocol_version = "HTTP/1.1"`(기본값 HTTP/1.0은 요청마다 연결을 새로 맺는다).
- `lookup()`: 함수 이름으로 목록을 찾고, 인자가 일치하는 항목의 `result`를 돌려준다. 없으면 규격 문서가 정한 "없음" 응답.
- 일치 판정과 정규화 범위는 09:00 규격 문서를 그대로 따른다. 서버를 "똑똑하게" 만들지 않는다. 채점 대상은 상담원이 보낸 인자다.
- 시험용 데이터로 바꿀 때는 프로세스를 완전히 다시 띄운다. 호출 기록이 메모리에 남지 않게 한다.
- 교체 절차를 미리 연습한다: 파일 저장, 재시작, `GET /tools`와 표본 조회 확인까지 1분 안에.

### 5.10 시연 모드 (사용자 경험 50점)

행사 전에 가짜 응답기로 끼어들기까지 동작하게 만들어 둔다. 당일 오후에 브라우저 음성 문제를 잡을 시간은 없다.

기본 동작

- `session.start`에 `"mode":"live"`가 있으면 `turn.end` 뒤에도 연결을 유지하고 다음 발화를 듣는다. 대화 이력은 서버가 쌓는다.
- 음성을 실제 재생 속도로 조금씩 보낸다. 끼어들기가 생기면 즉시 멈출 수 있다.

끼어들기

| 항목 | 설계 |
|---|---|
| 확정 조건 | 말소리가 160~200ms 연속으로 이어지거나, Soniox 토큰이 2자 이상 나옴. 프레임 하나로 끊지 않는다 |
| 동작 | 전송을 멈추고 `{"type":"agent.cancel"}`을 보낸다. 클라이언트는 재생 대기열을 비운다 |
| 이력 정리 | 실제로 재생된 부분까지만 `[중단됨]` 표시와 함께 이력에 남긴다. 다 말한 것으로 남기면 LLM이 고객이 끝까지 들었다고 착각한다 |
| 재생 위치 | 보낸 음성 길이와 문장 길이의 비율로 추정한다 |

에코 (스피커 소리가 마이크로 들어가는 문제)

1. 시연은 이어폰을 기본으로 한다.
2. 브라우저의 `echoCancellation: true`를 켠다.
3. 그래도 남는 것은 Soniox의 상담원 텍스트 입력이 걸러 준다. 공식 문서가 이 용도를 명시하지만 에코 제거를 대체하지는 않는다고 한다. 텍스트는 재생보다 0.5~1초 앞서, 재생 속도에 맞춰 조금씩 보낸다. 끼어들면 들려준 데까지만 보내고 `end_of_segment`로 닫는다.

시연 화면은 예약된 재생 노드를 모두 보관했다가 `agent.cancel`이 오면 일괄 정지한다. 마이크는 보안 컨텍스트에서만 열리므로 서버와 같은 노트북에서 `http://localhost`로 연다.

시연 화면 (`demo/index.html`)

- 마이크 입력, 스피커 출력.
- 진행 상황 표시: 받아쓰기, 완결성 판정, 추측 실행과 커밋 시각, 함수 이름과 인자와 결과, 답 문장.
- 턴별 지연을 겹침 막대로 보여 준다. 추측 실행이 무음 대기와 겹치는 모습이 그대로 보인다.
- 인계가 일어나면 인계 요약 카드를 띄운다: 고객 정보, 주문번호, 수행한 조치, 인계 사유.

| 즉시 연결 | 매뉴얼에 없는 정책 판단, 예외 요청 | 임의 답변 없이 연결 |

근거로 삼을 것: 매뉴얼의 연결 규정, 준수사항 3번("넘겨야 할 상황에서 AI가 계속 응대하면 안 됨"), 연습 문항의 정답 분포.

## 7. 속도와 품질

### 7.1 지연 예산

| 구간 | 단순 순차 방식 (추정) | 이 설계 (목표) | 줄이는 방법 |
|---|---|---|---|
| 말 끝에서 종료 확정 | 0.8초 (고정 무음 기준) | 0.5~0.9초. 미완결·서두는 최대 2.4초 | 의미 기반 종료 판단, 완결성에 따라 대기 시간을 달리함 |
| 받아쓰기 확정 | 0.1~0.3초 | 위 구간과 겹침 | 스트리밍 토큰으로 미리 진행, 커밋 시 검증 |
| LLM 결정과 첫 문장 | 0.5~1.0초 | 위 구간과 대부분 겹침 | 추측 실행, 프롬프트 캐시와 유지 요청, 연결 예열 |
| TTS 첫 음성 | 1.0~2.0초 | 캐시 적중이면 0 | 첫마디·정형 문장·대표 답변 캐시. 한도가 넉넉하면 추측 합성 |
| 함수 결과에서 답 첫 소리 | 1.5~3초 | 1.0~2.0초 | 캐시 적중, 접수형은 정형 문장 |

경로별 첫 소리

| 경로 | 첫 소리 | 비고 |
|---|---|---|
| 정형 문장·대표 답변 적중 | 커밋 직후 (말 끝에서 0.5~0.9초) | 합성 없음 |
| 함수 호출 | 커밋 직후, 안내 문구 | 사람 상담원도 하는 말 |
| 자유 생성 답, 추측 합성 켬 | 커밋 직후 | Plan A에서만 |
| 자유 생성 답, 추측 합성 끔 | 커밋 + TTS 첫 음성. 답 음성 대기 한도(1.35초)를 넘기면 중립 첫마디 | 중립 첫마디 비율을 지표로 관리 |

"단순 순차 방식"의 값은 추정이다. 오전에 최소 구현으로 실제로 재서 기준선으로 삼는다.

### 7.2 정확성을 위해 일부러 기다리는 지점

| 지점 | 기다리는 이유 | 비용 |
|---|---|---|
| 미완결로 보이는 발화 | 문장 중간의 긴 쉼에서 끼어들지 않기 위해 | 해당 문항의 첫 소리가 최대 1.6~2.4초 |
| 인사·서두만 있는 발화 | 인사 뒤에 본론이 이어지는 경우가 많다 | 인사만 하고 끝난 문항은 첫 소리 2.4초 |
| 추측과 확정 받아쓰기가 다름 | 틀린 번호로 답하지 않기 위해 다시 실행 | LLM 한 번의 시간 |
| 함수 호출 | 번호를 끝까지 들은 뒤에만 호출 | 추측 단계에서 조회 결과를 미리 쓰지 못함 |
| LLM 결정 대기 | 함수 호출 여부를 모른 채 안내 문구를 내지 않기 위해 | 말 끝에서 최대 1.2초 |

### 7.3 버린 대안

| 대안 | 버린 이유 |
|---|---|
| 고정 무음 기준(예: 800ms)으로 종료 판단 | 1초 넘게 쉬는 고객에서 끼어들기. 기준을 올리면 모든 문항이 느려진다 |
| 모든 답을 채움말로 시작 | 속도 점수는 오르지만 사용자 경험 감점 사례에 명시되어 있다 |
| 신경망 VAD, 턴 감지 모델 추가 | 지정 외 AI 모델 제한에 걸릴 수 있다 |
| 음성 에이전트 프레임워크 전체 도입 | 측정기 프로토콜이 독자 규격이고, 프레임워크의 턴 감지는 별도 모델에 의존한다. 커밋 게이트를 직접 제어하기 어렵다 |
| 상담원 서버가 모의 데이터를 직접 읽어 번호 보정 | 중계를 거치지 않는 조회는 측정기 우회로 볼 수 있고, 실제 서비스 구조와도 다르다 |
| STT 원문을 코드로 미리 숫자 변환 | 일반 표현을 망가뜨릴 수 있다. 변환은 문맥을 아는 LLM에 맡긴다 |
| 쉼마다 TTS까지 추측 | 요청 한도와 비용. 추측은 LLM까지만, 합성은 조건부 |
| 짧은 답을 문장마다 나눠 합성 | 요청 수가 늘고 문장 사이에 목소리가 튄다 |
| 마지막 토큰이 도착한 시각으로 무음 시작을 보정 | 토큰은 항상 음성보다 늦게 와서 모든 문항이 그만큼 늦어진다. 처리 진행값 확인으로 대신한다 |
| 첫마디와 함수 호출을 동시에 시작 | 첫마디 뒷부분이 조회 뒤 답으로 측정될 수 있다 |

### 7.4 09:00 실측에 따른 분기 (09:40까지 확정)

TTS 요청 수요: 동시 4건이면 분당 20~30문항이 지나간다. 문항당 합성 1회만 해도 분당 20~30회가 필요하다.

| 실측 결과 | 확정할 설계 |
|---|---|
| TTS 한도 분당 60회 이상, 첫 음성 1.2초 미만 | **Plan A**: 추측 합성을 조건부로 켠다. 정형 문장 캐시는 기본 범위 |
| TTS 한도 분당 30~60회, 또는 첫 음성 1.2~1.8초 | **Plan B**: 추측 합성을 끈다. 응답당 합성 1회. 정형 문장과 대표 답변 40개 이상을 미리 합성 |
| TTS 한도 분당 30회 미만, 또는 첫 음성 1.8초 이상 | **Plan C**: 캐시로 나가는 답의 비율을 70% 이상으로 올린다(대표 답변, 조회 상태별 안내 문장까지). 나머지는 세마포어로 줄 세운다. 운영진에게 한도 문제를 알린다 |
| 하루 한도가 시험 문항 수보다 적음 | 어떤 설계로도 감당할 수 없다. 즉시 운영진에게 제기한다 |
| Cloud TTS 키가 함께 제공됨 | 두 경로를 벤치마크하고 빠른 쪽 하나만 남긴다 |
| 채점 대상이 응답 음성의 받아쓰기 | TTS 입력 변환과 되받아쓰기 검증을 최우선으로 |
| 채점 대상이 `agent.transcript` 텍스트 | 텍스트와 음성의 일치만 지키고 TTS 변환 작업을 줄인다 |
| 연습 음성의 소음 바닥이 300에 가깝거나 넘음 | 적응형 임계값과 소음 경로를 켠다 |
| 조회 뒤 답의 기준표가 첫 소리보다 느슨함 (예: 만점 3.5초) | 조회 뒤 답은 한 번에 합성해 목소리 일관성을 우선한다 |
| 커밋(약 0.6초) + TTS 첫 음성이 1.35초 안 | 답 음성 대기 한도 1.35초 유지. 중립 첫마디가 거의 나오지 않는다 |
| 커밋 + TTS 첫 음성이 1.35~1.9초 | 1.35초 유지(속도 100점, 자유 답변마다 중립 첫마디)와 1.9초(속도 90점, 첫마디 감소) 중 고른다. 문항당 손실은 3점, 전체 100점 기준 최대 0.6점이라 사용자 경험 평가 방식을 보고 정한다 |
| `bench/probe.py`의 "결정" 칸 | 위 분기 중 해당하는 것을 바로 알려 준다 |

## 8. 측정과 실험

### 8.1 세션마다 남기는 시각

`말 끝 추정`, `쉼 감지`, `추측 시작`, `LLM 첫 토큰`, `LLM 결정`, `<end> 수신`, `커밋`, `검증 결과`, `함수 호출`, `함수 응답`, `TTS 요청`, `TTS 첫 조각`, `첫 프레임 전송`, `turn.end`. 한 줄에 한 세션씩 JSONL로 저장한다.

- 보고 값: 중앙값, 90% 지점, 95% 지점. 문항 수가 적으면 95% 지점은 참고용으로만 쓴다.
- 함께 세는 값: 추측 적중률, 문항당 추측 횟수, 중립 첫마디 비율, 캐시 적중률, TTS 요청 수.
- 말 끝 추정은 마지막으로 RMS가 임계값 이상이었던 프레임의 시각이다. 측정기의 정의와 같아서 측정기 없이도 첫 소리 시간을 스스로 잴 수 있다.
- 단계가 겹치므로 단계 시간의 합을 첫 응답 시간으로 쓰지 않는다. 발표에는 겹침 막대(단계별 시작과 끝) 도표를 쓴다.

핵심 실험 세 가지

| 이름 | 바꾸는 것 | 보는 것 | 산출물 |
|---|---|---|---|
| 종료 정책 | Soniox 종료 설정, 쉼 임계값, 커밋 규칙의 대기 시간 | 끼어들기 비율, 첫 소리 분포, 문항당 헛된 추측 횟수 | 끼어들기 0건인 설정 중 가장 빠른 것 |
| 프롬프트 | 프롬프트 버전, 정책 표, 추론 강도 세 구성, 대표 답변 캐시 사용 여부 | 응대·함수 점수, LLM 첫 토큰 시간 | 버전별 점수표, 틀린 문항의 유형 분류표 |
| 개선 전후 | 단순 순차 방식과 최종 구조 | 세 점수와 지연 분포 | 발표 3, 6, 8, 9번 슬라이드의 도표 |

여유가 있을 때

- Soniox 컨텍스트와 상담원 텍스트 입력이 받아쓰기 오류를 줄이는지. 틀린 문항 분류에서 받아쓰기 오류가 많이 보일 때만 한다.
- TTS 말투 지시 문구의 세부 조정.

### 8.4 비용 관리

- 한 문항의 추정 비용은 약 $0.004~0.006이다(STT 15초, LLM 2~3회 호출에 캐시 적용, 음성 6초). 400문항 전체를 한 번 돌리면 약 $2다. 벤더 가격 기준이며 크레딧 플랫폼의 환산은 다를 수 있다.
- 추측 실행의 LLM 호출은 캐시가 적용되면 한 번에 약 $0.001이라 비용 부담은 작다. 부담이 되는 것은 TTS 요청 수다.
- 채점기의 받아쓰기와 채점 비용은 따로 든다.
- 프롬프트 개선은 텍스트 전용 평가로 하고, 음성 전체 측정은 버전을 확정할 때만 한다.
- TTS 결과를 디스크에 캐시해 같은 문장을 다시 합성하지 않는다.
