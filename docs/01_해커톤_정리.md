## 2. 과제 내용 [사이트]

### 2.1 대상 상담 업무

| 유형 | 주요 업무 |
|---|---|
| 배송 | 주문 상태, 배송 현황 확인 |
| 주문 취소 | 취소 가능 여부 확인 및 처리 |
| 반품·환불 | 반품 접수, 환불 절차와 진행 상태 안내 |
| 교환 | 교환 문의 및 접수 |
| 결제 | 결제 수단, 입금, 결제 관련 문의 |
| 상품 | 제품 정보, 가격, 이용 방법 |
| 상담원 연결 | AI가 해결하기 어려운 문의의 인계 |

업무마다 확인 절차와 응대 정책이 다릅니다.

### 2.2 전화 상담의 세 가지 어려움

1. 고객은 기다려 주지 않는다. 2~3초 침묵이면 통화가 끊긴 것으로 느낀다.
2. 음성 정보는 불완전하다. 주문번호를 잘못 말하거나 정정하고, 맥락을 생략한다. "공일공"과 "영일영"처럼 같은 숫자를 다르게 말한다.
3. 업무 처리는 정확해야 한다. 확인되지 않은 정보를 안내하거나, 필요한 정보 없이 업무를 실행하면 안 된다.

### 2.3 예시 상황 (가상 예시, 실제 문항 아님)

| 케이스 | 고객 발화 | 봐야 할 것 |
|---|---|---|
| 배송 조회 | "제가 주문한 상품 언제 도착해요? 주문번호는 1234예요." | 주문번호 인식, 정보 충분성, 조회 결과에 근거한 안내, 불필요한 대기 없음 |
| 취소·환불 | "어제 취소 요청했는데 아직 환불이 안 됐어요." | 취소와 환불 상태 구분, 상태 확인 필요성, 확인 안 된 환불 일정 금지, 정책 준수 |
| 불명확한 요청 | "아까 그거 있잖아요. 그거 취소된 거 맞아요?" | 이전 대화 파악, 대상 주문 확인, 잘못된 주문 처리 금지, 자연스러운 추가 질문 |
| 상담원 연결 | "제품을 먹고 몸이 불편한데 어떻게 해야 하나요?" | AI 처리 가능 여부, 안전 주의, 사람에게 인계, 인계 정보 전달 |

### 2.4 핵심 과제와 미션 질문

- Challenge 1 속도: 발화 종료를 판단하고 가능한 빨리 첫 음성을 낸다. 목표는 첫 응답 1.5초 이내. "잠시만 기다려주세요" 반복은 좋은 경험이 아니다.
- Challenge 2 정확성: 전화번호·주문번호를 정확히 인식하고 필요한 기능을 호출한다. 필수 확인 절차를 생략하면 안 된다.
- Challenge 3 처리 범위: 모든 문의를 AI가 끝낼 필요는 없다. 무엇을 자동화하고 언제 인계할지 설계한다.
- 정해진 정답 아키텍처는 없다. 팀의 선택과 근거가 차별점이다.

## 3. 통신 규격

### 3.1 측정기 ↔ 상담원 서버 [사이트][킷][실행]

| 단계 | 내용 |
|---|---|
| 연결 | 문항 하나가 WebSocket 연결 하나 |
| 시작 | 연결 직후 JSON 텍스트 `session.start`가 온다 |
| 입력 | 16kHz, 16-bit signed little-endian, mono PCM. 20ms(640바이트)씩 실제 말하는 속도로 온다 |
| 무음 | 말이 끝난 뒤에도 무음 프레임이 계속 온다. 발화 종료는 팀이 판단한다. 말 중간에 1초 넘게 쉬는 고객도 있다 |
| 출력 | 같은 형식의 PCM 바이너리로 응답 음성을 보낸다 |
| 종료 | 응답을 마치면 `{"type":"turn.end"}` 텍스트를 반드시 보낸다. 함수를 호출했다면 결과로 답한 뒤에 보낸다 |
| 끼어들기 | 고객이 말을 마치기 전에 응답 음성을 보내면 끼어든 것으로 처리된다 |
| 제한 | 고객 말이 끝나고 25초 안에 `turn.end`가 없으면 측정기가 연결을 끊는다 |

`session.start` 예시 [킷]

```json
{"type":"session.start","session_id":"DEMO-1-abc","case_id":"DEMO1","now":"2026-11-21 11:00",
 "history":[],"caller":null,"tools_url":"http://localhost:8100",
 "audio":{"encoding":"pcm_s16le","sample_rate":16000,"channels":1}}
```

- `caller`는 null일 수 있다. 값이 있으면 `{"name","phone","email"}` 형태다. [킷]
- `history`는 "이번 말 이전까지의 대화 이력"이다. 데모에서는 전부 빈 배열이라 형식은 [미확정]이다.
- 문항마다 고객 발화 음성은 1개다. 여러 턴이 이어지는 음성은 없다. [Q&A]
- 예시 서버는 `{"type":"agent.transcript","text":"..."}` 텍스트 이벤트도 보낸다. 측정기는 이것을 `agent_text`로 모은다. [킷]

### 3.2 모의 함수 서버 [사이트][킷]

| 경로 | 역할 |
|---|---|
| `GET /tools` | 함수 목록과 정의. 제공되는 함수 정의와 같아야 한다. 골격은 `[{"type":"function","function":{...}}]` 형태로 돌려준다 |
| `POST /tools/{name}` | JSON 입력 → 정해진 JSON 출력. 정의에 없는 함수는 거부한다 |
| `GET /calls?session_id=` | 세션별 호출 기록. 연습용 측정기가 읽는다 (스타터킷에만 명시) |

- 실제 업무 로직은 필요 없다. 주어진 데이터에서 입력에 맞는 기록을 찾아 정해진 출력을 돌려주면 된다.
- 데이터는 실행할 때 파일로 읽는다. 최종 측정 직전에 운영진이 시험용 데이터 파일 하나를 건네고, 그 파일로 서버를 다시 띄운다.
- 데이터 구조(데모): `{함수명: [{"arguments": {...}, "result": {...}}]}`
- 응답 규칙의 세부는 11/21 규격 문서를 따른다. [미확정]

### 3.3 함수 중계 [사이트]

- 측정기는 상담원 서버와 모의 함수 서버 사이에 중계를 둔다. `session.start`의 `tools_url`이 중계 주소다.
- 함수는 `POST {tools_url}/tools/{name}`으로 부르고, `X-Session-Id` 헤더에 세션 ID를 넣는다.
- 헤더가 빠지면 호출하지 않은 것으로 채점한다.
- 모의 함수 서버 주소를 코드에 고정하면 최종 측정에서 호출이 기록되지 않는다.
- 상담원 서버에서 `tools_url`(운영진 노트북의 중계)로 나가는 연결이 되어야 한다.

## 4. 평가

### 4.1 전체 배점 [사이트][템플릿]

| 항목 | 배점 | 평가 방식과 내용 |
|---|---|---|
| 사용자 경험 | 50 | 심사위원 정성 평가. 응답 간결성, 응답 전달성, 사용자 니즈 충족성, 돌발 상황 대응 가능성 |
| 응답 품질 및 기능 구현 | 20 | 운영진이 비공개 시험 문항으로 측정. 시스템 총점(100) ÷ 5 |
| 발표 및 질의응답 | 20 | 설계 근거, AI 처리 범위와 상담원 연결 기준, 속도와 품질의 절충 설명 |
| 최종 기획서 | 10 | 문제·사용자 정의, 시스템 구조, 상담원 연결 기준, 피드백 반영 |

### 4.2 시스템 점수 = 응대 50% + 함수 20% + 속도 30% [사이트]

| 요소 | 비중 | 기준 |
|---|---|---|
| 응대 | 50% | 매뉴얼에 맞게 가격·정책·절차·조회 결과를 틀리지 않았는가. 문항별 맞음 1.0 / 괜찮음 0.7 / 틀림 0 |
| 함수 | 20% | 맞는 때에 맞는 전화번호·주문번호로 호출했는가. 호출하면 안 될 때 호출해도 틀림 |
| 속도 | 30% | 고객 말이 끝난 뒤 첫 소리까지의 시간. 함수 문항은 조회 뒤 실제 답까지의 시간도 본다 |

속도 점수표

| 시간 | ≤1.5초 | ≤2.0 | ≤2.5 | ≤3.0 | ≤3.5 | ≤4.0 | ≤5.0 | ≤6.0 | 초과 |
|---|---|---|---|---|---|---|---|---|---|
| 점수 | 100 | 90 | 80 | 70 | 60 | 50 | 30 | 10 | 0 |

- "확인해 보겠습니다" 같은 채움말도 첫 소리로 인정한다.
- 함수 문항의 속도 점수는 첫 소리 점수와 조회 뒤 답 점수의 평균이다.
- 소리를 내지 않거나, 연결에 실패하거나, 고객이 말하는 도중에 첫 소리를 내면 그 문항의 속도는 0점이다.
- 채점기는 받아쓰기와 채점에 OpenAI API를 쓰므로 키가 필요하다. 같은 측정기·채점기로 연습 문항 점수를 미리 볼 수 있다.

연습용 측정기의 실제 계산 방식 [킷]

| 값 | 계산 |
|---|---|
| `first_sound` | 측정기에 도착한 프레임 중 RMS 300 이상인 첫 프레임의 도착 시각 − 말 끝 시각 |
| 말 끝 시각 | `meta.json`의 `speech_end` (음성 파일 안에서 마지막 유성 구간이 끝나는 시점) |
| `spoke_before_end` | 첫 유성 프레임이 말 끝보다 먼저 도착 |
| `after_tool_sound` | 마지막 함수 응답 이후에 도착한 첫 유성 프레임까지의 시간 |
| 속도 0점 조건 | `spoke_before_end`, 오류, `turn.end` 없음, `turn.end`가 25초 초과 |
| 기본 동시 접속 | 4 (`--concurrency`) |

공식 측정기는 11/21에 공개되므로 계산 방식이 같은지 당일 코드로 다시 확인해야 합니다.

### 4.3 사용자 경험 평가 기준 [사이트]

심사위원이 보는 것

- 불필요한 말을 반복하지 않는가
- 고객의 요구를 정확하게 파악하는가
- 응답 속도가 실제 대화에서 자연스러운가
- 고객이 말하는 도중에 개입하거나 추가 질문을 했을 때 대응할 수 있는가
- 응답이 간결하고 명료한가
- 고객이 원하는 업무가 자연스럽게 완료되는가

감점 사례

| 사례 | 고객이 겪는 문제 |
|---|---|
| 필요 이상으로 긴 답변 | 음성으로는 끝까지 듣기 어렵다 |
| 모든 답변에 같은 채움말 | 같은 말을 계속 듣게 된다 |
| 이미 전달된 정보를 다시 묻기 | 맥락을 기억하지 못하는 상담원으로 느껴진다 |
| 핵심 요구를 놓침 | 정확한 답이어도 업무가 끝나지 않는다 |
| 중간 개입 무시 | 정정이나 추가 질문이 반영되지 않는다 |
| 지나치게 빠르지만 부자연스러움 | 말을 마치기 전에 답하거나 리듬이 어색하다 |
| 정확하지만 응답 시간이 김 | 침묵이 길면 통화가 끊겼다고 오해한다 |

### 4.4 발표·질의응답 점검 항목 [사이트]

- 시스템 구조를 왜 이렇게 설계했는가
- 같은 모델에서 왜 이 처리 순서와 응대 방식을 골랐고, 개선 전후에 무엇이 달라졌는가
- 어디까지 AI가 처리하는가, 어떤 경우 사람에게 연결하는가
- 속도와 응대 품질의 trade-off를 어떻게 판단했는가
- 개발 중 어떤 문제가 있었고 어떻게 개선했는가
- 질문에 기술적 근거로 답할 수 있는가

## 5. 준수사항 [사이트]

1. 제공 자료의 안내를 따른다. 공식 자료의 사용법은 그 자료의 문서와 현장 안내가 기준이다.
2. 스타터킷은 연습용이다. 스타터킷 점수는 공식 점수가 아니다.
3. 응대 매뉴얼과 브랜드 정보를 따른다. 매뉴얼에 없는 정책을 지어내거나, 받아야 할 정보 없이 함수를 호출하거나, 넘겨야 할 상황에서 AI가 계속 응대하면 안 된다.
4. 모의 함수 서버는 팀이 직접 만든다. `tools_url`과 `X-Session-Id`를 쓴다.
5. 시스템 평가는 행사 당일 오후, 운영진 노트북의 측정기가 비공개 시험 문항으로 직접 측정한다.
6. 측정 시간에는 두 서버를 켜 둔다. 운영진은 서버를 제공하지 않는다. 문항 4개가 동시에 들어온다. 측정 중에는 서버를 고치거나 다시 띄우지 않는다.
7. 제공 데이터는 대회 안에서만 쓴다. 측정 중 사람이 대신 답하기, 시험 음성 저장·유출, 측정기 우회는 실격 사유다.
8. 시스템 점수만을 위한 설계를 지양한다. 모든 응답을 채움말로 시작하는 방식은 좋은 설계로 보지 않을 수 있다.
9. Human Handoff 기준을 직접 정의하고 기획서와 발표에서 설명한다.
10. 직접 만든 시스템을 기술적 근거로 설명할 수 있어야 한다.
11. 정해진 시간 안에 제출한다.

Q&A로 추가 확인된 규칙 [Q&A]

- `speak()`를 Tool Call로 구현해도 된다. 구현 방식 제한은 없다.
- 오픈소스 레포를 Fork해서 수정·활용해도 된다.
- GPU 서버 지원은 없고 외부 API를 쓴다.
- LLM은 GPT-5.4 mini 하나다. (초기 Q&A의 "3종 중 선택" 문구는 최종 공지로 대체됨)

## 7. 지정 모델 검증 결과 [공식문서]

### 7.1 Soniox STT `stt-rt-v6`

| 항목 | 내용 |
|---|---|
| 접속 | `wss://stt-rt.soniox.com/transcribe-websocket`, `Authorization: Bearer <키>` 헤더 |
| 순서 | 연결 → 설정 JSON(텍스트) → 음성(바이너리) → 빈 텍스트 프레임으로 종료 → `"finished": true` |
| 오디오 | `audio_format: "pcm_s16le"`, `sample_rate: 16000`, `num_channels: 1` 이면 측정기 음성을 변환 없이 전달 |
| 토큰 | `text`, `start_ms`, `end_ms`, `confidence`, `is_final`. 비최종 토큰은 바뀔 수 있고 최종 토큰은 다시 오지 않는다 |
| v6 출시 | 2026-11-03. 숫자·ID·이름 인식 개선, 컨텍스트 활용 강화, 상담원 텍스트 입력 기능 추가 |

발화 종료 감지 (`enable_endpoint_detection`)

- 무음만 보지 않고 쉼, 억양, 대화 맥락으로 판단하는 의미 기반 방식이다. 끝났다고 보면 구간을 확정하고 `<end>` 토큰을 보낸다.
- 조절 값 세 가지

| 파라미터 | 범위 | 기본값 | 효과 |
|---|---|---|---|
| `endpoint_latency_adjustment_level` | 0~3 | 0 | 높을수록 종료를 빨리 낸다. 종료가 더 자주 나고 정확도가 조금 떨어질 수 있다 |
| `endpoint_sensitivity` | -1.0~1.0 | 0.0 | 높을수록 종료를 쉽게 낸다. 중간에 자주 쉬는 화자에게는 음수 값 |
| `max_endpoint_delay_ms` | 500~3000 | 2000 | 말이 끝난 뒤 종료 신호가 나오는 최대 지연 |

- 문서가 권하는 저지연 시작점: level 2, sensitivity 0.3, max delay 1500. "1초 넘게 쉬는 고객"이 있는 이번 과제에는 그대로 쓰기 위험하다.

수동 확정

- `{"type":"finalize"}`를 보내면 그때까지의 음성이 확정되고 `<fin>` 토큰이 온다.
- 말이 끝난 뒤 약 200ms의 무음을 보낸 다음에 호출하라고 한다. 너무 자주 보내면 연결이 끊길 수 있다(몇 초에 한 번은 괜찮다).

컨텍스트 (`context`)

- `general`(짧은 사실 2~8쌍), `text`(긴 배경), `terms`(고유 명칭). 전체 8,000 토큰 이하.
- 한국어는 한글로, 브랜드명은 평소 표기대로 쓴다.
- `terms`에 숫자, 코드, 전화번호는 넣지 말라고 한다.
- 통화마다 발신자 정보(이름 등)를 추가하라고 권한다.

상담원 텍스트 입력 (`enable_agent_text_input`, v6 전용)

- `{"type":"agent_text","text":"...","end_of_segment":true}`로 상담원이 한 말을 보내면, 모델이 고객 답을 그 맥락에서 받아쓴다. 짧고 모호한 답에서 효과가 크다.
- 두 번째 효과: 마이크로 새어 들어온 상담원 음성을 고객 말과 구분해 받아쓰기에서 뺀다(문서 표현은 "agent voice echo cancellation"). 단, 에코 제거를 대체하지 않으므로 기존 에코 제거는 켜 두라고 한다.
- 텍스트는 실제 재생 시점보다 0.5~1초 앞서, 재생 속도에 맞춰 조금씩 보내야 한다. 한꺼번에 보내면 안 된다.

### 8.2 실행 결과 [실행]

- 환경: Python 3.12.10, `websockets` 17.4(신규 설치), `httpx` 0.28.1, `numpy` 2.5.5, `scipy` 1.18.1
- 1차(삐 소리 서버): 3문항 모두 첫 소리 0.75~0.78초, 속도 100, 오류 없음, 동시 3건 처리
- 2차(`--demo-tool`): DEMO3에서 `request_callback({"phone_number":"01000001234"})` 호출, `X-Session-Id`가 세션 ID로 기록됨, 응답은 `not_implemented`
- 결과 파일: 킷 폴더의 `runs/demo/`, `runs/demo_tool/`

실행에서 확인한 사실

- 0.77초는 거의 전부 무음 800ms 대기 시간이다.
- 측정기는 프레임 도착 시각만 본다. 재생 속도에 맞춰 보낼 필요가 없다.
- 데모 음성 분석: 문장 안의 쉼이 최대 640ms(DEMO1), 580ms(DEMO2)다. 800ms 기준을 아슬아슬하게 통과한다. 음성 앞에는 0.5~1.0초, 뒤에는 0.13~0.2초의 무음이 있다.

### 8.3 코드에서 고쳐야 할 것 [킷]

| 문제 | 영향 | 조치 |
|---|---|---|
| 모의 서버가 `127.0.0.1`에만 열린다 | 운영진 중계가 접속하지 못한다 | `0.0.0.0`으로 바인딩 |
| 데이터 경로가 `data/demo_*.json`으로 고정 | 시험용 파일로 교체하기 번거롭다 | 실행 인자로 경로를 받게 수정 |
| `lookup()` 미구현 | 조회 결과가 없다 | 인자 일치 항목의 `result` 반환 |
| 예시 서버의 무음 800ms 기준 | 1초 넘는 쉼에서 끼어들기 0점 | 의미 기반 종료 판단으로 교체 |
| 측정기가 완료 문항을 건너뛴다 | 재측정 시 결과가 안 바뀐다 | 매번 새 출력 폴더 사용 |

### 8.4 V1과 V2의 차이 [킷]

- 가상 음성이 영어 합성음에서 한국어 합성음으로 바뀌었다.
- 파일을 열 때 `encoding="utf-8"`을 지정하도록 고쳤다(Windows 오류 방지).
- `--demo-tool` 예시가 `get_order_info`에서 `request_callback`으로 바뀌었다.
- V1 README의 "공식 채점 395문항"과 V1 문서의 "14개 공식 기능" 문구가 삭제됐다. [미확정]
- V1은 음성 길이와 `meta.json`의 말 끝 시각이 맞지 않는다. V2만 쓴다.

- [ ] Gemini 2.5 Flash TTS의 분당·일일 한도는 얼마인가
- [ ] `tools_url`(중계)은 행사장 내부 주소인가. 클라우드에 올린 서버에서도 닿는가
- [ ] 시스템 측정 시각과 팀 순서
- [ ] 사용자 경험 50점은 무엇을 보고 평가하는가 (발표 시연, 측정 녹음, 심사위원 직접 통화)

키를 받자마자 잴 것

- [ ] Gemini TTS: 첫 음성 조각까지의 시간, 스트리밍 조각 크기, 동시 4건에서의 오류
- [ ] Gemini TTS: 글 길이별(약 25자, 60자, 120자) 첫 음성 시간. 길이에 따라 늘어나는지
- [ ] Gemini TTS: 분당 한도와 하루 한도. 동시 4건이면 분당 20~30회가 필요하다
- [ ] Gemini TTS: 말투 지시문을 소리 내어 읽지 않는지
- [ ] GPT-5.4 mini: 첫 토큰까지의 시간 (`none`과 `low` 비교, 캐시 적중 시)
- [ ] Soniox: 받은 키의 리전. 미국 주소로 접속되는지, 일본 주소(`stt-rt.jp.soniox.com`)여야 하는지
- [ ] Soniox: 말 끝에서 `<end>`까지의 시간 분포, 한국어 숫자 인식 형태
- [ ] 연습 음성: 무음 구간의 소음 바닥(RMS). 300에 가까운지
- [ ] 행사장 네트워크에서 운영진 노트북 → 우리 서버 접속 (Windows 방화벽 인바운드 허용 포함)
- [ ] 행사장 Wi-Fi와 USB 테더링을 함께 연결했을 때 API 호출이 테더링으로 나가는지
